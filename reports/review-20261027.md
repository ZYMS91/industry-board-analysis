## ② 错误清单（5 条；习惯错在前）

### 习惯错 · 第1次 · 提交了一个从没跑通的脚本
- 现象：`summarize.py` 第 9 行 `down=(int(df["涨跌幅"]<0).sum())`，`.venv\Scripts\python.exe summarize.py` 实测 `TypeError: int() argument must be ... not 'Series'`，退出码 1；该状态已 commit（`6cdaf01`，21:55），工作区干净。
- 根因：第 8 行 `up=int((...).sum())` 括号在外，第 9 行括号套在内，改完没有保存后重跑一遍就提交。把「写完」当成「跑过」。
- 正确做法：任何改动，先 Ctrl+S，再跑一次脚本，看到末行是期望输出再 `git commit`。
- 下次自检：`git commit` 之前跑一次被改脚本，`echo %ERRORLEVEL%` 必须等于 0；不是 0 就不许 commit。

### 习惯错 · 第1次 · 打补丁：写错的推导式注释掉留在原地 + 调试 print 没删
- 现象：第 21 行留着 `#alloed = {str(v),for v in nums.values()}:`（错在逗号，且拼写 alloed）；第 13 行 `print(nums)` 把整个 dict 打进了正式输出。
- 根因：改正时把错的那行注释掉、在下面另写一行，而不是删掉重写；调试语句用完不清理。——与你改文件中「插入正确内容而不删旧内容」的老毛病同源（10-24 那次动相邻行、10-26 README 只换文字不删旧格式，是同一个动作习惯）。
- 正确做法：错误行直接删，不留注释尸体；调试用的 `print` 在收尾时全删，只留对外要输出的那几行。
- 下次自检：commit 前 `grep -n "^#" summarize.py`，输出里不许出现被注释掉的代码（只允许中文说明注释）；`grep -n "print(" 文件` 逐行确认每条都是要输出的。

### 技术错 · 第1次 · 校验是同源自证，拦不住幻觉
- 现象：`text = f"... {n} ... {up} ... {down} ... r={r} ... {conc}%"`，`check_numbers(text, nums)` 用 `re.findall(r"-?\d+\.?\d*", text)` 抽出数字，与 `{str(v) for v in nums.values()}` 比对——文案就是 `nums` 变出来的，除非有人手改文案，否则永远通过。
- 根因：把「让代码跑通」当成「让校验有效」。判据原文是「摘要里的每个数字都能在 `stats.py` 输出里找到」，比对基准应该是 `stats.py` 的 stdout，而不是本脚本自己的中间变量。
- 正确做法：基准数字从 `stats.py` 的实际输出里取（跑一遍、解析、或直接 import 它的函数），文案另写；校验失败必须能用一个"故意写错的数字"复现。
- 下次自检：校验写完后立刻做反向实验——把文案里 `r=-0.297` 手改成 `-0.99` 跑一次，必须报「不通过」，报不出来就是校验无效。

### 技术错 · 第1次 · 失败信号与崩溃信号都是退出码 1
- 现象：`check_numbers` 失败走 `raise SystemExit(1)`；今天的 `TypeError` 崩溃也是退出码 1（实测 `EXIT=1`）。看退出码无法区分「校验成功拦住幻觉」和「脚本根本没跑起来」。
- 根因：只设计了「通过/不通过」两种语义，没给「自己崩了」留第三种。
- 正确做法：校验不通过用 `SystemExit(2)`，通过打印固定标记并 `0`；未捕获异常天然是 1，从此三者可分。
- 下次自检：跑完立刻 `echo %ERRORLEVEL%`，只有 0 和 2 是预期值，1 一律按"脚本崩了"处理，先去读 traceback。
