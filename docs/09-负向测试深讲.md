# 负向测试深讲（2026-11-27）

> 起因：首测第 3 题问「`with pytest.raises(...)` 里面的代码如果正常跑完，测试算过还是挂」，
> 答成「过，就是让报错」——**目的说对了，判定说反了**。这一篇讲透。

## 一、断言的两种方向

| | 写法 | 什么时候算过 |
|---|---|---|
| 正向测试 | `assert 结果 == 期望` | 结果**等于**期望 |
| 负向测试 | `with pytest.raises(某异常):` | 被包住的代码**必须抛**这个异常 |

负向测试验的不是「结果对不对」，而是「**坏东西一定会被拦住**」。

## 二、`pytest.raises` 内部在做什么

它不是一个装饰器，是一个**上下文管理器**，干的活等价于：

```python
try:
    with pytest.raises(SystemExit):
        被包住的代码
except 指定的异常:
    pass          # 抓到了 → 通过（异常被吃掉，测试不中断）
else:
    raise Failed("DID NOT RAISE SystemExit")
```

**最关键的一点：它自己把异常吃掉了。**
你写 `pytest.raises` 之后，被包住的异常不会冒出来打死测试，而是"抓到了记一分"。
没有它，异常会把测试直接判成失败（见下面 C）。

## 三、三种情况实测（真跑出来的）

测试代码：

```python
def boom():   raise SystemExit(1)
def quiet():  return "没事发生"

def test_A_有raises且真抛():
    with pytest.raises(SystemExit): boom()

def test_B_有raises但没抛():
    with pytest.raises(SystemExit): quiet()

def test_C_没raises却抛了():
    boom()
```

结果：

```
demo.py::test_B_有raises但没抛 FAILED
    E   Failed: DID NOT RAISE SystemExit

demo.py::test_C_没raises却抛了 FAILED
    E   SystemExit: 1

2 failed, 1 passed
```

| 情况 | 结果 | 说明 |
|---|---|---|
| A 有 raises，代码真抛 | ✅ passed | 抓到异常 → 过 |
| B 有 raises，代码没抛 | ❌ FAILED: **DID NOT RAISE** | 等异常没等到 → 挂 |
| C 没 raises，代码抛了 | ❌ FAILED: SystemExit: 1 | 异常把测试打挂，**不是**"通过" |

结论：`pytest.raises` 不是可有可无的修饰，**它是唯一能把"抛异常"变成"通过"的东西**。

## 四、只写 `pytest.raises(SystemExit)` 不够 —— 三种「假绿」

项目现在的测试（`tests/test_summarize.py` 第 106–110 行）：

```python
with pytest.raises(SystemExit):
    check_numbers(text, nums)
```

它能证明"有东西被拦住了"，但证明不了**是谁拦的、为什么拦**：

| 假绿 | 后果 |
|---|---|
| 抛的是别的 `SystemExit`（比如命令行解析出错） | 也照样通过 |
| 「数字无法溯源」和「字段值缺失」两种失败 | 分不清是哪一种 |
| 不知道具体哪个数字出了问题 | 排查时瞎猜 |

## 五、升级写法（项目里实测可行）

`summarize.py` 里的异常定义给了我们细节：

```python
class NumberMismatch(SystemExit):
    def __init__(self, offenders, missing):
        self.offenders = list(offenders)                # 文案里有、白名单里没有的数字
        self.missing = sorted(str(m) for m in missing)  # 白名单里有、文案里没出现的值
        super().__init__("文案校验未通过（" + "；".join(parts) + "）")
```

于是可以断言到细节：

```python
from summarize import NumberMismatch

with pytest.raises(NumberMismatch, match="无法溯源") as e:
    check_numbers(text, nums)

assert e.value.offenders == ["0.5"]   # 拦下来的正是这个数字
assert e.value.missing == []          # 没有字段缺失
```

三个新东西：

- **`match=`** 用正则匹配异常**文字**（实测：`pytest.raises(SystemExit, match="无法溯源")` 通过）
- **`as e`** 拿到异常对象，`e.value` 就是它
- **`NumberMismatch` 比 `SystemExit` 更精确**：项目自己的子类，别的 SystemExit 混不进来

### 一个必须知道的坑

`raise SystemExit("文字")` 时：

- `e.value.code` = **那段文字**，不是 1
- 但进程**退出码仍然是 1**（Python 的约定：SystemExit 带文字 → 打印到 stderr，退出码 1）

所以「退出码 1」这件事在测试里要靠 `e.value.code` 的类型或内容来判断，不能指望它等于 1。

## 六、负向测试的三条纪律

1. **断言到具体异常类**，不要一律 `Exception` / `BaseException`
2. **`pytest.raises` 只包住"必须报错的那一行"**，包太大就会把别处的错也吃成绿色
3. **改坏要验红**：故意把条件改成"应该能通过"，测试必须变红；不红说明测试是假的

## 七、面试一句话

> 负向测试不是"跑一下看它崩不崩"，而是断言它**必须抛指定的异常**；只断言"会抛错"等于没断言，因为抛错的原因可能完全不相干。

# 附录：`with pytest.raises(SystemExit):` 逐词拆解（2026-11-27 补）

## 1. 四个部分

```python
with  pytest.raises(SystemExit):      ← ① with ② 表达式 ③ 冒号
    check_numbers(text, nums)         ← ④ 缩进块（被包住的代码）
```

| 部分 | 是什么 | 说错会怎样 |
|---|---|---|
| `with` | 关键字，启动**上下文管理器**协议 | 少了它，`pytest.raises(...)` 只是个没人用的对象，异常照样打挂测试 |
| `pytest.raises` | `pytest` 模块里的**函数** | —— |
| `(SystemExit)` | 传给函数的**异常类**（类型本身，不是实例） | 传 `SystemExit()` 会 `TypeError`（见下） |
| `:` + 缩进 | 被检查的代码块 | 缩进范围写大了，别处的错也被吃成绿色 |

## 2. `pytest.raises(SystemExit)` 求值得到的是一个**对象**

它不是「断言函数」，是「造一个上下文管理器」。
`with` 语句拿这个对象，做两件事：

```python
cm = pytest.raises(SystemExit)
cm.__enter__()      # 进入：记录开始
try:
    缩进块
except SystemExit:  # 抓到目标异常
    通过               # 且不再往外抛
finally:
    cm.__exit__(...)  # 退出：判断到底过不过
```

`__exit__` 的判断：

- 抓到目标异常 → 回去 `True` → 异常**被吞掉**，测试通过
- 没抓到 → 主动 `Failed("DID NOT RAISE ...")`
- 抓到的是别的异常 → 不管，继续往外抛 → 测试失败

## 3. `SystemExit` 是什么东西（实测）

```
SystemExit 的继承链: ['SystemExit', 'BaseException', 'object']
issubclass(SystemExit, Exception) = False
```

所以：

- `except Exception:` **抓不到** `SystemExit`（`summarize.py` 第 35–38 行的注释正是这个理由：不能让「校验失败」被降级成「LLM 不可用」）
- `sys.exit(1)` 就是 `raise SystemExit(1)` 的另一种写法
- `raise SystemExit("文字")` → `e.code` 是那段**文字**，进程退出码仍是 1；`str(e)` 也是那段文字

## 4. 错写清单

| 错写 | 结果 |
|---|---|
| `pytest.raises(SystemExit())` | `TypeError: Expected a BaseException type, but got an exception instance` |
| `pytest.raises("SystemExit")` | 同上，字符串不是异常类 |
| `pytest.raises(Exception)` | 能跑，但太宽——任何错误都算过（假绿） |
| 把 `assert` 写进缩进块 | `AssertionError` 不是目标异常 → 测试挂，看起来像"被测代码坏了" |
| 缩进块写成一整个流程（准备+执行） | 准备阶段的错也算"通过" |

## 5. 逐行读项目那 5 行

```python
def test_写死的测试会被拦下():          # pytest 靠 test_ 前缀发现它
    nums = {"行数": 90, "上涨": 23}      # 准备：白名单（只有 90 和 23）
    text = "今日 90 个板块中，上涨 23 个（阈值 0.5）。"   # 文案里多了 0.5
    with pytest.raises(SystemExit):       # 断言：下面这行必须抛
        check_numbers(text, nums)         # 执行：0.5 不在白名单 → raise NumberMismatch
```

一句人话：**「我准备好一份只有 90 和 23 的白名单，再给一段多了 0.5 的话，然后断言校验一定会炸。」**

## 6. `as e` 拿到的不是异常

```python
with pytest.raises(NumberMismatch, match="无法溯源") as e:
    ...
```

`e` 是 `ExceptionInfo` 对象，**异常本身在 `e.value`**。所以断言写 `e.value.offenders`，不是 `e.offenders`。
